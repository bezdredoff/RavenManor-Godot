## 2. Selection and completion rule (every gate kind)

Define eligible(beat, request) as the **conjunction**, never a single tap boolean:

1. Approved canonical dialogue `status=runtime_approved` and route `approvedRuntime=true`/`proposedRuntime=false`; Foundation beat registration; real accepted portraits/backgrounds/cues and full RU/BE/EN, stable ordered line IDs. Owner/content/route approvals remain independent.
2. **Immediately preceding canonical beat** is present in freshly loaded `storyBeatsSeen` AND the current beat is absent. The ordinal alone orders eligible scenes; it does **not** enforce prerequisites. In particular 02-02 requires 02-01, not merely Chapter I done.
3. The selected action has the correct **type and exact canonical ref**, matched to an accepted authored map target and current NPC/prop/door/service availability. The route's `interactionTarget` is a **descriptive string**, not proof of a click or a stable `RM-HS-*` ID. Do not dispatch from selecting a room thumbnail or tapping arbitrary ground.
4. The production gameplay host (not a UI/view/QA caller) owns the pending request, asks the real authored navigation controller to move Evelyn, then validates real arrival: current room, exact interaction or door anchor/target, connected authored route, no active actor segment, no unresolved portal transition, expected request still pending, and actor footpoint distance ≤ `0.25` world units. Door-triggered scenes also require validated traversal and far-side arrival where authored. Existing `Dispatch.next_scene_at_confirmed_hotspot` validates host identity, non-draft source, graph/anchor, no segment or transition, and the footpoint; it **does not** yet prove typed NPC/object/door/service ref.
5. **After** arrival, reload/recheck predecessor, beat-not-seen, target presence/state, door unlock, room safety and specialist outcome. Match the canonical `{gate.kind, gate.ref, interactionTarget, roomId, arrivalAnchor}`; discard in-memory request context on cancellation, reload, new request or target change. No persisted fake tap receipt and no externally supplied `approved`/`arrived`/`repair_complete` booleans.
6. Dispatch via accepted canonical scene only. On `RavenVNPlayer.advance()` reaching the real last line, `Dispatch.completion_event` proposes `story_beat_seen`. Only `RavenReducer.apply` and `RavenCampaignStore.save_campaign` write the canonical one-shot progress; completion is never recorded on route arrival, dialog open, read-only Skip or early close.

**Trust separation:** controller/actor establishes *physical arrival*, host-integrator binds *exact interaction intent*, reducer/store establishes *durable story state*, approved catalogs establish *executable content*. None can substitute for another. The current reducer checks that a story flag ID is registered, not the provenance of a repair, so a future trusted specialist coordinator must protect that caller boundary.

After `story_beat_seen` succeeds, repeat interaction is an approved inspect/no-op, not VN reward/replay or a second progression event. Reducer event-ID and already-known-beat idempotence protect double commits.

**Continue nuance:** `position_checkpoint` is allowed only at verified **safe** anchors, not moving, threshold or arbitrary interaction anchors. `reload_session` reconstructs from persisted safe room/anchor. `vnCursor` proves an unfinished line, **not** a fresh arrival or permission to start a scene. The existing host's `configure` only restores an in-progress production scene when a confirmed hotspot matches a physical anchor. A last-saved safe anchor can differ from the interaction anchor: this is a real future multi-room integration gap requiring re-approach/revalidation + cursor resume tests. Do not "fix" it by persisting an invented tap receipt or saving unsafe coordinates.

Required future **trusted service workflow**, solely in an integration-owner implementation:

2. Conduct the actual specialist visit/work/safety inspection after the area is made accessible; a UI click, queued appointment, powered-on background or a successful minigame cannot mark completion.
3. Only on genuine specialist completion and internal validated signoff, apply an owner-approved **Foundation-registered durable result** using existing reducer/store. Do **not** introduce or pre-write a speculative story flag, `RM-REST-*` ID, or custom serialized receipt here. 4. Save succeeds **before** the room appears safe or 02-04 becomes eligible. Recheck outcome and physical kitchen arrival to start the VN; service completion alone never auto-starts the scene.
5. Retry is idempotent; failed/cancelled specialist work, failed save or reload without committed outcome leaves 02-04 closed. Do not rely on a Match-3 checkpoint as contractor evidence.

**Save schema and migration decision:** A simple persisted *completed* specialist outcome can use already-present `storyFlags` or `completedRestorations` (after reviewed Foundation ID/real event mapping), so `raven_snapshot.gd` schema v1 needs **no change for these contracts**. Registered future beats/rooms/doors/hotspots can likewise be added to their existing Foundation collections under the sole integration owner without necessarily changing the schema; normalization is registry-aware. If gameplay later truly requires durable *pending appointment stages*, external contractor acknowledgments or restart-safe partial repair state not derivable from existing primitives, that is a **separate** reviewed schema/migration decision with old-save, corrupted-save and write-failure tests. It is neither required nor authorized in this contract PR.

## 6. Explicit save, one-shot, cancellation and failure acceptance

- **Before interaction:** restore from approved safe room/anchor; no pending movement survives restart; re-evaluate target/gate on next real request.
- **On arrival:** if safe checkpoint is allowed, reducer/store may persist position; otherwise do not persist an interaction/door threshold as safe. No scene beat event yet.
- **VN in progress:** existing localized `vnCursor`/`vnReadLines` and read-only Skip apply; no advancing across unread lines/choice gates. On Continue, revalidate canonical scene, predecessor and interaction, re-approach if needed and restore the cursor without a new seen event.
- **On genuine end:** `story_beat_seen` once; reducer first, atomic store save second, UI success only after write. Duplicates and repeat taps do not grant work points or progress twice.
- **On cancel/error:** clear host in-memory pending intent. Wrong/unknown ID, wrong room, target despawn, incomplete movement, pending transition, locked/unreviewed door, unsafe kitchen, interrupted VN, old/failed save, corrupted state → **no promotion, no seen flag, no fake arrival**. Existing host safe-hold applies on failed save.
