# Raven Manor — аудит CODE/GAP P0 и графа зависимостей
**Дата:** 2026-11-03. **Объект:** текущий `main` после смерженного #150, PR только с планом/метаданными/проверками.

## Предпосылка и правила

В исходных production-схемах `code_work_packages.json` и `gap_work_packages.json` всё ещё было **34 CODE P0 + 54 GAP P0 = 88 старых P0**. Большая часть либо доставлена в нескольких мерджах, либо является исторической широкой постановкой с нативным QA как отдельным выходом. Цель — сохранить scope и evidence, но показывать в панели реальную очередность. На это **не** накладывается бездоказательный статус `accepted`.

`production_progress.json` теперь задаёт приоритет `P0/P1/P2` не только для GFX, но и для CODE/GAP ID. У записи без предшествовавшего progress override появляется `status=proposed` с `implementationState=not_recorded` — **не реализовано и не принято**, но нынешний приоритет явно определён. Исторический `code_work_packages.json` неизменен (`PROPOSAL_NOT_RUNTIME`), а `gap_work_packages.json` сохраняет исходные приоритеты в качестве части истории разработки; их `status` остаётся синхронизирован с live progress.

## Аудит зависимостей

Из отдельного исходного CODE/GAP планирования выявлены **две реальных цикла**:

- `VNS5-09 → VNS5-11 → VNS5-09`.
- `VNS5-09 → VNS5-12 → VNS5-09`.

Исправление: `VNS5-11` зависит от уже реализованных authored staging/reorder `VNS5-07B` и `VNS5-07F3`; `VNS5-12` зависит от `VNS5-11`, графических проводов `VNS5-07C3` и FX `VNS5-07F5`. Только итоговая `VNS5-09` e2e-проверка зависит от `VNS5-11/12`. Recovery `VNS5-10` должна зависеть от draft authoring `VNS5-06B`, а **не** от VNS5-09. Начальный read-only VNS5-00 audit независим от позже superseded editor-архитектуры.

В историческом CODE-плане сохранились поставленные пакеты, формально связанные с открытыми подэтапами (например, `CODE-02-02/04 → CODE-02-01`, `CODE-08-02 → CODE-07-02`), потому что это **связи исходного production-плана**, а не основание заново исполнять успешный merge. **Не меняем исходные CODE scope/dependsOn без отдельной архитектурной причины.**

Теперь дашборд показывает отдельно **«Активные зависимости»** (`openDependsOn`) и **«Исторические связи плана»** (`dependsOn`). Для задач с завершённым статусом активные блокеры пусты. Для реально открытой `CODE-02-06` остаётся необходимый `CODE-02-05`, например. Граф проверяется в Linux/Windows CI командой `python3 scripts/raven/tools/validate_backlog_dependencies.py`: отсутствие неизвестных IDs, циклов, self-refs, зависимостей открытой задачи от superseded/deferred, запрет P0 у архивных задач, точность `openDependsOn`.

## Контрольные числа

- Исторические **88** CODE/GAP P0 → **6** реальных активных CODE/GAP P0;
- Совместно с GFX P0 → **13** реальных P0;
- `production_progress.json` содержит explicit overrides для всех 88 старых CODE/GAP P0, в том числе ранее отсутствовавших ID;
- Никаких статусов артового approval, merge, устройства, stage/story/routing/save и исходных файлов code/art не меняем;
- `reconcile_gap_statuses.py --check` продолжает возвращать **0 status mismatch**;
- Исторические CODE/GAP dependencies не выбрасываются, но текущий blocker-граф имеет собственный проверяемый интерфейс.

**Следующее содержательное решение** после очистки: выбрать очередность реальной проверки, а не начинать новую генерацию. Сначала QA VN Studio/локализаций/mobile ZIP, затем Hall geometry + Match-3 и только после утверждения нужных спрайтов — map chibi. Приоритет Hall в P0 отражает текущий vertical-slice gate, а не команду немедленно заниматься искусством.
