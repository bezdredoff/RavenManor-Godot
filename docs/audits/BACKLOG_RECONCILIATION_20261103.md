## Почему старый NEXT_PLAN больше не работает

Предыдущий `docs/NEXT_PLAN.md` был Hall pipeline diary от 2026-10-25 с наложением от 2026-11-02, где планировалось «merge PR #137», снова развивать VN prop catalog и выполнять уже сделанные package steps. Такое описание нельзя считать рабочей очередью. Полная оригинальная история без потери данных перенесена в `docs/audits/NEXT_PLAN_HALL_PIPELINE_ARCHIVE_20261025.md`.

Новый `docs/NEXT_PLAN.md` — **единственный человекочитаемый текущий список следующей работы**, разделённый на QA-only, исправления функциональности, новые ассеты и отдельно отложенные решения. Фактические task statuses по-прежнему в `production_progress.json`, не в текстовой таблице.

## Предохранители и оставшиеся решения

- Новый `reconcile_gap_statuses.py --check` — детерминированный QA двух реестров. Запускается в `scripts/check.sh` и `check.ps1`. `--sync` разрешает исправить только статус при наличии authoritative progress entry; не создаёт фальшивые approvals и не меняет CODE baseline.
- У `VNS5-09` исправлен один устаревший статус после фактического мержа. Другие технически смерженные задачи **не** автоматически переводятся в `accepted`.
- Все широкие GitHub issues сохраняются. Нельзя закрывать #121 только потому, что закрыты части VN Studio, или #3 только по green vertical-slice CI.
- Нужны отдельные решения об архитектуре Hall `GFX-08-02`, приоритетах remaining CODE/GAP P0, применимости map чиби в текущей вертикальной версии и необходимости реального `VN-RUNTIME-01` для ветвления. Их нельзя «решить» одним status sync.
- Дашборд формируется генератором. `dashboard/status.json` **не редактировать вручную**.

**Вывод:** backlog и source-of-truth очищаются от исторических расхождений; все настоящие неготовые компоненты сохранены, при этом работа без прямой нужды в текущей игре не получает фальшивого `accepted`.
